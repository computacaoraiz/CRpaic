What it covers:

- Project context: what CRpaic is, and how the v2 branch (modules, crpaic_
  prefix on every public name) differs from the older v1 API on master.

- Build: the main make commands and options (MODE=DEBUG, CSTD, install and
  uninstall). Two easy-to-miss rules:
  - Warnings are treated as errors, including implicit narrowing conversions.
  - The version must match in both include/CRpaic/CRpaic_version.h and
    src/VERSION.TXT, or the build stops.

- Tests:
  - The CUnit tests in tests/ link against the installed library, not the copy
    built in the repo.
  - They still use the old v1 names (get_int and so on), so they haven't been
    updated for v2. 
  - There's no way to run a single test.

- Architecture:
  - CRpaic.h is the one header users include. It pulls in one header per module,
    and each module is split into smaller parts with matching files in include/
    and src/.
  - Functions like crpaic_max and crpaic_min work for any number type. This
    relies on GCC extensions, which is why the build needs gnu17. 
  - Folders that are drafts or reference material and aren't built: todo/,
    experimental/, gpt/. 

- Conventions: the file templates and section order, the comment and formatting
  style, and how man pages and their examples are written.

I only ran the build as a dry run and didn't compile or run the tests.

O que entendi

A CRpaic é uma biblioteca de apoio para alunos que estudam pelo Programming
Abstractions in C, do Roberts. Ela se inspira no cslib e na libcs50, mas é mais
enxuta: deixa de fora o que "facilita demais", como GetBlock e New, porque aluno
de PAIC deve usar a libc diretamente.

- v1 (2024, master): um único CRpaic.h + CRpaic.c, com as get_*, substring,
  ithchar e concat, mais testes em CUnit.

- v2 (2025, v2, 2.0.0 ainda não lançada): biblioteca modular com prefixo
  crpaic_. Os módulos I/O e math estão prontos. As funções genéricas usam
  _Generic com extensões do GCC e _Static_assert; por isso o build é gnu17 sem
  -Wpedantic. Todas as get_* passam por crpaic_vget_string, para não quebrar o
  atributo format. As strings são liberadas por um destrutor no fim do programa.

- O que falta: testes da v2 (os de tests/ ainda são da v1),
  gcd/lcm/clamp/prev_prime, datas, os módulos String/Char portados de
  todo/src/CRpaic.c, estruturas de dados com ponteiros opacos e, mais adiante,
  SQLite, ICU e raylib. Para distribuir, você já pesquisou pkg-config, .deb/APT
  e Read the Docs.

1.2 Design do módulo I/O (para discutirmos)

- D1. NOPROMPT é " \b": isso escreve 2 bytes de verdade na saída, e confirmei
  com od que eles aparecem quando a saída vai para um arquivo ou pipe. Testei
  que crpaic_get_string(NULL) não gera aviso com -Wall -Wextra, ao contrário de
  "", que dispara -Wformat-zero-length. Então #define NOPROMPT NULL resolve.

- D2. O construtor deixa o stdout sem buffer para todo o programa:
  - Com a .so, isso vale até para um programa que só usa math.
  - Com a .a, só vale se charstr.o for linkado, então o comportamento muda entre
    link estático e dinâmico (vi isso no teste).
  - Saída sem buffer é muito mais lenta.
  - Alternativa: chamar fflush(stdout) depois de imprimir o prompt.

- D3. Toda linha lida fica na memória até o fim do programa: isso inclui as
  tentativas inválidas e as linhas usadas por dentro de get_int. Um laço que lê
  10^6 inteiros guarda 10^6 strings. Além disso, o buffer cresce 1 byte por
  caractere e o array de strings cresce 1 posição por chamada, o que é
  O(n²). Sugiro que get_int e as outras get_* numéricas liberem a própria linha,
  que só get_string registre a string para liberar no fim, e que o crescimento
  seja geométrico.

- D4. free() na string de get_string causa double free na saída do
  programa. Isso conflita com o objetivo primário, porque o aluno precisa
  aprender a usar free. Opções: 
  - (a) documentar "nunca libere";
  - (b) criar crpaic_free_string, que tira a string do registro;
  - (c) tirar o registro e deixar o aluno liberar.

- D5. A biblioteca não é thread-safe (usa um array global). Basta documentar.

- D6. get_float e get_double recusam notação científica (1e3). Vírgula e locale
  também não estão definidos. Precisa de uma decisão.

- D7. Falta __attribute__((format(printf, 1, 0))) em crpaic_vget_string.

- D8. Valores sentinela ambíguos: em erro, get_char devolve CHAR_MAX (127, que é
  um caractere válido), e INT_MAX não pode ser digitado. Isso veio da libcs50;
  vale decidir conscientemente se fica assim.

1.3 Módulo math, consistência e build

- Há dois estilos misturados: os wrappers de is_prime são static inline no
  header, e as outras funções são extern. Convém escolher um padrão, porque isso
  afeta a ABI.

- A regra de "mesmo tipo" é boa, mas faz crpaic_max(x_long, 0) falhar; o aluno
  precisa escrever 0L. Isso deve estar documentado na man page.

- #ifndef string não tem efeito, porque string é um typedef e não uma macro.

- O ramo para MSVC no INITIALIZER é código morto, já que a biblioteca só suporta
  Linux.

- Expressões ? true : false são redundantes.

- No Makefile:
  - CFLAGS := impede o usuário de acrescentar flags.
  - O clean faz find ... -exec rm -fr no repositório inteiro, o que é arriscado.
  - A conferência com VERSION.TXT repete o que CRpaic_version.h já diz.
  - Sugiro acrescentar -Wformat=2 -Wshadow -Wmissing-prototypes e talvez
    -fvisibility=hidden.

- Comentários desatualizados e erros de digitação:
  - a documentação de vget_string cita _crpaic_get_string(&args, &format);
  - "CRpaic_id_charstr.h";
  - "unsiged", "lont", "int64_4", "stanard", "flot", "funcionts".

- O README ainda descreve a API da v1.

- CRpaic.h já inclui stdio.h, stdlib.h e outros headers por conta própria. Isso
  conflita com o objetivo de não esconder demais? A decisão é sua.

1.4 O que está bom

- Estrutura modular limpa: as fontes são encontradas automaticamente e o build
  gera .a, .so e objetos PIC.

- vget_string é robusta: verifica SIZE_MAX, trata CR, LF e CRLF, usa ungetc e
  libera a memória em todos os caminhos de erro. O valgrind não acusou nada.

- O _Generic com _Static_assert dá mensagens de erro claras e avalia cada
  argumento uma única vez (testei com x++).

- is_even e is_odd estão corretas para negativos.

- next_prime acerta os limites: (char)127 devolve 0 com ERANGE, e INT_MAX - 1
  devolve INT_MAX.

- Comentários de interface e man pages com exemplos são um ótimo padrão.

2.2 Escolha do framework

+--------------+----------+----------+-----------+-----------+
| Critério     | CUnit    | cmocka   | Criterion | Próprio   |
+--------------+----------+----------+-----------+-----------+
| Mantido      | não      | sim      | pouco     | por você  |
| Pacote apt   | sim      | sim      | sim       | n/a       |
| Isola testes | não      | não (*)  | fork      | não (*)   |
| Timeout      | não      | não (*)  | sim       | não (*)   |
| Mocks/falhas | não      | sim      | não       | --wrap    |
| Saída TAP    | não      | sim      | sim       | fácil     |
| Filtro teste | não      | sim      | sim       | fácil     |
+--------------+----------+----------+-----------+-----------+
(*) resolvido com um executável por submódulo, rodado sob timeout

Recomendo o cmocka. É C puro, é mantido, está no apt (libcmocka-dev), permite
simular falhas de malloc e realloc (é o que o SQLite faz de mais importante),
gera saída TAP e JUnit para CI e permite filtrar um único teste. O CUnit não tem
release desde 2018.

2.3 Duas mudanças pequenas no código para facilitar os testes
